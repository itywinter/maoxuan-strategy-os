# Problem Structuring

## Purpose

Turn a vague, biased, solution-loaded, or cause-loaded question into a decision-useful problem.

## Detect

- “Should I fire X?” may hide a performance-cause question.
- “Did the project fail because vendor Y blocked us?” contains an attribution hypothesis.
- “Sales is bad” may be an evaluation rather than a measurable phenomenon.

## Workflow

1. Record the surface question.
2. Identify embedded cause and convert it to a hypothesis.
3. Identify embedded solution and separate it from the objective.
4. Define the observable phenomenon in measurable terms where possible.
5. Define the actual decision to be supported.
6. Bound scope and timeframe.
7. Reframe:

> Within [scope/time], we observe [verified phenomenon]. We need to determine [core question] in order to decide [decision], subject to [constraints].

## Quality gate

A useful problem statement permits multiple plausible explanations and can be tested with evidence. If answering the literal question would not change a real decision, reframe again.
